# Проверка Indicators & Work Dashboard по основным запросам

Здесь описано, что можно делать в каждом модуле и как проверить результат понятными шагами. Сверка выполнена для версии 1.3.0 на 9 октября 2026 года. Есть сценарии существующих функций и критерии приёмки предстоящих функций. Наличие сценария не означает, что функция уже сделана или проверка пройдена.

Главный рабочий цикл: **увидеть показатель → заметить проблему → выбрать работу → выполнить → проверить результат и модель → вернуться к показателю**. Часы, готовность работы и изменение характеристики системы проверяются отдельно.

## Как читать сценарий

Gherkin — описание проверки обычным языком с несколькими служебными словами. Формат и русские ключевые слова соответствуют [документации Cucumber](https://cucumber.io/docs/gherkin/reference/).

- **Функция**: зачем нужен модуль и что в нём можно делать.
- **Сценарий**: одна ситуация, которую проверяем.
- **Допустим**: что подготовлено до начала проверки.
- **Когда**: какое действие выполняем.
- **Тогда**: какой видимый результат ожидаем.
- **И**: дополнительное условие, действие или ожидаемый результат.

Например, I01: заданы отдельные нормы чтения и руководств → записаны 2 часа чтения → чтение получает 20%, руководства этих часов не получают. Это проверка смысла учёта, а не цвета карточки.

Если в сценарии несколько действий, выполняй их по порядку. После каждого «Тогда» сверяй результат на экране или в доступной таблице. Один сценарий можно повторять с разными тестовыми объектами.

## Где доступна функция

| Метка в файле | Значение |
| --- | --- |
| `@implemented_local` | Функция существует в локальном редакторе по коду и имеющимся тестам. Эта метка не утверждает, что конкретный ручной сценарий уже пройден. |
| `@cloud_snapshot` | Проверка опубликованного закрытого снимка Sites. В версии 1.3.0 облако допускает просмотр, не ведение новых записей. |
| `@planned` | Критерий будущей функции. До реализации результат проверки — «Ожидает реализации». |
| `@external_source` | Нужны реальный источник, устойчивые связи и проверка импорта. |
| `@cloud_write` | Нужна запись в облаке, которой у текущего снимка нет. |
| `@device_check` | Проверяется на настоящем телефоне; запуск на ПК этого не подтверждает. |

Метки `@req1`–`@req7` связывают сценарии с пунктами владельца; `@req5_1` обозначает норматив на конкретную задачу. Пункт 8 фиксирует границу текущего запроса: новые модули вне этого списка здесь не добавляются.

## Как провести первую ручную проверку

Начни с текущих функций. Для пробных записей можно запустить отдельный редактор с пустым каталогом данных. В новом окне PowerShell выполни:

```powershell
Set-Location -LiteralPath 'C:\Users\Lenovo\Documents\ChatGPT\Повышение собранности, руководства\work-productivity-tool'
$env:DASHBOARD_DATA_DIR = Join-Path (Get-Location).Path 'outputs\acceptance-sandbox\data'
$env:DASHBOARD_DATA_FILE = Join-Path $env:DASHBOARD_DATA_DIR 'dashboard.json'
$env:DASHBOARD_PORT = '8791'
$env:DASHBOARD_VIEWER_PORT = '8792'
node server.mjs
```

Открой [тестовый редактор](http://127.0.0.1:8791/). Это самостоятельный набор пробных данных. Проект назови «Тестовый сервис». Временные даты выбирай относительно сегодняшнего дня; в расчётах используется Asia/Tashkent. Остановка этого тестового сервера — Ctrl+C в его окне PowerShell.

| Порядок | Действие | Сценарий и результат |
| --- | --- | --- |
| 1 | Создай тестовый проект и объект, сохрани описание и следующий ход, затем дополни запись. | M02: текст переживает повторное открытие, прежняя версия видна в истории. |
| 2 | Поставь дату возврата сегодня и включи «Пора вернуться». | M03: объект попадает в список возврата. |
| 3 | Задай отдельные нормы чтения и руководств, запиши 2 часа чтения. | I01: чтение 20%, руководства не получают чужое время. |
| 4 | Запиши проблему дня и один результат с конкретным следующим ходом. | D01: важное видно в блоке «Сегодня». |
| 5 | Создай две задачи до эксплуатации и закрой одну. | W01: открытой остаётся одна задача; смена этапа проекта её не закрывает. |
| 6 | Создай кейс и сохрани две диагностики. | C02: обе записи доступны, следующий ход актуален. |
| 7 | Создай тестовую цель: база 20 дней, цель 5 дней, замер 10 дней. | G01: уменьшение, 67%, дата и свидетельство. |
| 8 | Сверь запись времени с недельным фактом в «Данных». | B01: таблица и показатель согласованы. |

Этот маршрут проверяет существующие части. Для облака отдельно проверь B03–B06. T01–T09 и полный цикл E01–E02 остаются ожидающими реализации; их нельзя зачесть вместо проверки готового таймера.

## Как записать результат

В [manual-run.csv](manual-run.csv) есть отдельная строка каждого сценария. Открой файл как UTF-8, чтобы сохранить русские буквы. Столбец «Где проверять» описывает доступность функции, столбец «Результат проверки» — фактический результат твоего прогона.

- **Не проверено**: функцию ещё не проверяли этим сценарием.
- **Пройдено**: выполнены все шаги и совпали все ожидаемые результаты.
- **Не пройдено**: функция доступна, но хотя бы один результат не совпал; запиши факт и приложи свидетельство.
- **Ожидает реализации**: соответствующая функция ещё не сделана.
- **Недоступно для проверки**: например, нет телефона или доступа к источнику; укажи причину.

Для каждой проверки записывай версию, дату, устройство, фактический результат и свидетельство. Предстоящая функция и обнаруженный дефект — разные записи. Непройденный сценарий не исправляется изменением ожидаемого результата под текущую ошибку.

## Связи и правила учёта

1. **Норматив времени** описывает усилия: например, часы на выбранную работу. **Годовая цель** описывает желаемое изменение системы. **Результат дня** описывает конкретный продукт или изменение, которое хотим получить сегодня.
2. Работу можно связать с системой и указать ожидаемый вклад в её три приоритета и ограничитель. Ожидаемый вклад не заменяет замер характеристики и не доказывает причинность.
3. Рабочие минуты и количество полных помидорок считаются отдельно. Паузы и перерывы не входят в рабочую норму. Два сеанса по 15 минут и один по 50 минут дают 80 минут, даже если следующий пресет будет 25 минут.
4. Одна запись времени выполняет один основной часовой норматив. Сводки по задаче, проекту и цели могут показывать тот же интервал как разные разрезы; общий итог не складывает эти разрезы повторно.
5. «Вне норм» не тождественно «не туда». Работа без недельного плана может помогать важной цели, а работа по норме может не дать результата. Для надзора нужен собственный выбранный фокус и явная классификация; неизвестное остаётся для разбора.
6. Неполный учёт не описывает все сутки. Неизвестные факты, отсутствующая шкала и невыбранный ориентир остаются No Data.

## Что требуется решить для годовых целей

Текущая локальная модель поддерживает числовые замеры. Портфель источника также содержит текст, диапазоны, наблюдения «да/нет», проверку чек-листом и качественные уровни. Их нельзя молча переводить в точное число или процент.

Для каждой выбранной карточки нужны: исходная цель и система, 1–3 важные характеристики, ограничитель при необходимости, определение шкалы, текущий факт с датой, ориентир и частота проверки. Свободные описания систем и целей сохраняются; стандартизируется способ наблюдения, а не содержание всех целей.

Для текстовой цели возможна шкала с описанными уровнями. Если используется условная доля по уровням, она должна быть подписана. Для «да/нет» можно показывать состояние или долю подтверждённых наблюдений за период с известным охватом. Для диапазона требуется выбрать правило порога; до этого — No Data. Конкретные шкалы и выбор 3–4 карточек остаются решением владельца.
