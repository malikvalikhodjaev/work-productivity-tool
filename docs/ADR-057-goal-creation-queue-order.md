# ADR-057 · Последовательность создания строк и переносов

Дата: 2026-10-27. Клиент 0.1.45+47, сервер 1.33.1.

После установки 0.1.44 владелец вручную разрешил три конфликта moveGoal. Проверка отдельной копии SQLite подтвердила пустую очередь, отсутствие ошибок и сохранение исходников в conflictHistory. Изолированный повтор прежних 19 команд воспроизвёл ровно те же три отказа. У каждого различался только sortOrder новой строки, без расхождения её родителя. Реальные данные для воспроизведения не изменялись и не включаются в репозиторий.

Причина: проекция goals заранее добавляла все локальные черновики новых строк, затем применяла предыдущие перемещения. Ещё не созданная на сервере строка получала порядок от более раннего переноса. Следующее перемещение сохраняло подпись такой структуры, хотя при последовательном исполнении сервер ещё не назначал новой строке sortOrder. Простой повтор исходной команды возвращал тот же отказ. Это ошибка проекции собственной очереди, а не подтверждение действий другого устройства.

Теперь новая строка, отсутствующая в каноническом снимке, добавляется в проекцию ровно на месте соответствующей saveGoal в очереди. До её первого переноса sortOrder остаётся null, как на сервере. Уже известная серверу строка не вставляется заново. Исходные requestId, payload, expectedHierarchy, тексты, связи и факты ранее отправленных команд не переписываются. Незавершённые тексты остаются в SQLite. Настоящее изменение структуры на сервере по-прежнему требует решения владельца.

Для конфликта «Иерархия индикаторов уже изменилась» окно объясняет, почему повтор не поможет. Вместо него доступны «Применить перенос к текущей структуре» и «Оставить серверный вариант». Первое действие использует существующее подтверждение, свежую структуру и проверку допустимости переноса; исходник сохраняется в истории. Автоматического выбора локальной версии нет. Другие виды отказов сохраняют возможность повторить неизменённую команду, например после исправления серверной валидации.

Дополнительно сервер 1.33.1 согласован с формой ручного замера цели: комментарий необязателен, до 3000 символов, хранится точно с пробелами и абзацами. Пустой комментарий не блокирует остальные команды. Для замера характеристики системы прежнее требование подтверждения сохраняется. Исторические факты не меняются; повтор UUID не создаёт второй замер.

Проверки: несколько созданий между перемещениями ветвей; подпись перед каждым шагом; отсутствие влияния будущих строк на предыдущие шаги; потеря HTTP-ответа после создания, файловое переоткрытие и идемпотентный повтор; неизменность исходных команд; сохранение точных текстов; понятный выбор при настоящем конфликте; необязательный комментарий к ручному замеру без обрезания и без дубликата по UUID. 29 выбранных клиентских сценариев и 176 серверных тестов прошли; анализ lib чистый. Установка фиксируется отдельно.
